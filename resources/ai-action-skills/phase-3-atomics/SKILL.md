# Phase-3 agent atomics — authoring skill

> Written from the 16 atomics waves shipped between 2026-06 and 2026-08 (~716 `audience:'ai'` actions across 24 pieces), and revised after reviewing what actually needed fixing once those PRs merged. Every rule below traces to something that went wrong once — the PR numbers are kept so you can check the claim rather than trust it.

Thin orchestrator over AP's `piece-builder` skill. It does NOT re-teach action authoring — it adds the six things piece-builder lacks for Phase 3: (1) authoring from a reviewed audit spec, (2) the agent-atomic body idioms, (3) the OAuth-scope-expansion check, (4) the Tier-2 connection test, (5) the per-atomic `outputSchema` (authored from the Tier-2 captured output), and (6) the `minimumSupportedRelease` floor (piece-builder only ships it as a scaffold literal for *new* pieces — step 7). Proven end-to-end on the Gmail pilot (2026-06-25) — the four gmail label/trash atomics are the canonical reference.

**⚠ Scope per piece: full agent-surface parity, not a handful of atomics.** Cover every vendor capability an agent could need — a *coverage map* (see Inputs), not a 1–4-atomic add-list. Author an `audience:'ai'` atomic for each vendor endpoint worth exposing (composites included), re-author overlaps as twins, and demote per step 5. At this scale a piece typically lands 15–80 atomics; waves 1–8 shipped ~716 across 24 pieces. The recipe below (author → scope-check → aiMetadata → register → Tier-1/Tier-2) is unchanged; the google-docs pilot is the worked reference — read it at **#14519** (the merged squash), not the closed #13926. **Composites + table/coordinate atomics are the bug-prone ones (every Greptile finding on the pilot landed there) — give them extra review; simple 1:1-endpoint atomics held up clean.** Post-merge review of all 16 PRs (2026-08-11) confirms this and adds the two classes the pieces team had to fix *after* merge, both in `atomic-templates.md`: **partial-update clobbering** (§6) and **vendor capability flags modeled as props** (Props notes).

## Inputs (per piece)
- **A reviewed coverage map for the piece** — the atomics to add, the existing actions to demote, what to skip, and a reviewer's verdict. **Only author from an approved map.** The 40 maps produced for waves 1–8 live in the AI-ready planning workspace (Ibrahim's — ask him) (`plans/specs/<piece>.md`); for a piece with no map yet, produce one first:
  1. List the piece's live surface — every action in `src/index.ts`, marked broad/multi-intent where it bundles several jobs.
  2. List the vendor's real endpoints for the app (its own public API docs are the authority — every atomic must map 1:1 to a real endpoint). Optionally cross-check your list against any third-party agent-tool catalog your team already uses, purely as a *checklist* of which narrow tools a mature platform thought worth shipping — never as a source of params or prose, which must come from the vendor's docs. Skipping the cross-check is fine; skipping the vendor docs is not.
  3. Classify each candidate **augment** (capability the piece lacks), **twin** (an agent-shaped re-wrap of an existing action → demote the original per step 5), or **skip** (already covered) — with a one-line reason each.
  4. **Adversarial review before authoring.** A second pass — a fresh subagent given the map plus the vendor docs and told to *disprove* it, or a teammate — checks every endpoint, param and ID format actually exists. Waves 1–8 ran this as a subagent review and it rejected 5 of 40 maps for fabricated endpoints and ID-format hazards, so it is not a formality. Self-review by the agent that wrote the map does not count; a fresh context is the point.
- The piece dir: `activepieces/packages/pieces/community/<piece>/` — its `src/index.ts` `actions:` array is the LIVE surface; its `src/lib/auth.ts`, `common/`, and an existing action are the convention source of truth (golden rule: match the piece, not these templates).

## Recipe
1. **Read** the AP repo's **`piece-builder` skill — `.agents/skills/piece-builder/`** (also symlinked under `.claude/skills/`): its `SKILL.md` + `ai-metadata.md` + `props-patterns.md`, and `output-quality.md` for the required flat-output shape. It ships in the monorepo, so a normal checkout has it; **this skill is a thin layer on top and assumes you have read it.** Then read the target piece's existing actions + `auth.ts` + `common/`.
2. **Author each atomic** as `createAction({ auth, name, displayName, description, audience: 'ai', aiMetadata: { description, idempotent }, props, run })` — one file per action under the piece's actions dir, matching the piece's client/auth/error-handling style. Body idioms per archetype: see `atomic-templates.md`.
3. **OAuth-scope-expansion check (load-bearing — the #1 pilot gotcha).** Write atomics (create/modify/delete/label) usually need a broader scope than the piece's read+send actions request. Compare each atomic's `vendorEndpoint` required scope against the scopes in `auth.ts`. If a scope is missing, **add it** (e.g. Gmail needed `https://www.googleapis.com/auth/gmail.modify` for labels/trash/batchModify). ⚠️ Adding a scope means **existing connections must be re-consented** (their stored token predates the scope) — flag this in the PR and for Tier-2.
4. **`aiMetadata`**: description = what + when-to-pick-over-sibling + key constraint (1-3 sentences, no output shape); `idempotent` derived from what `run()` does (read/get-or-create/PATCH-by-id → true; create/send/delete/multi-step → false). Get-or-create idempotency is **contingent on the wrapper** (list-first → return existing on conflict) — implement it, don't just claim it.
5. **Reuse-twins + demotion** (the parity rule — goal: a uniform `audience:'ai'` agent surface with no human-shaped duplicates visible to agents). For each existing `'both'` action that overlaps an agent intent your map covers, pick one:
   - **No `ai` atomic covers that intent yet → add a distinctly-named `ai` twin (reuse the original's `run()`), then demote the original `'both' → 'human'`.** The twin needs a NEW unique `name` — two actions can't share one, and you can't rename the original without breaking existing flows. Worked refs: `create_document` (human) + `create_text_document` (ai); `read_document` (human) + `get_document` (ai).
   - **Another `ai` atomic already covers the intent → just demote the original `'both' → 'human'`, NO twin** (a twin would duplicate it). Ref: `find_document` demoted, covered by `search_documents`.
   - **A narrower new atomic genuinely supersedes a coarse action → demote it.** Ref: `append_text` → `human` (superseded by `insert_text`).
   - **No agent equivalent anywhere in the map → leave `'both'`.** Ref: `create_document_based_on_template` (template-merge — no agent-shaped counterpart).
   Demotion is **discovery-only** — `audience` is read by agent discovery (`ap_search_actions`), never by the engine / `ap_run_action` — so human flow-builder usage is unaffected. Only demote after the covering `ai` atomic/twin passed Tier-2.
   **Guard the demotion against a competing `audience` write.** Curation PRs and sibling waves write `audience` on the same actions; two branches writing different values merge into a duplicate object key, and whoever fixes the build picks a winner — silently undoing the demotion. Worked case: #13941 demoted 6 google-sheets actions, #14428 tagged the same 6 `'both'`, the build fix (`3b8d5e5`) kept `'both'` — so 6 duplicate-intent pairs (each demoted original beside its `sheets-*` twin) are live on the agent surface today. Before demoting, `gh pr list --search '<piece>'` for other open PRs on the piece; after your PR merges, re-read the served `audience` of every action you demoted.
6. **Register**: import + add to the `actions:` array in `src/index.ts` (before `createCustomApiCallAction`).
7. **Version + release floor**: PATCH-bump the piece `package.json` (new actions = PATCH; a new *required* prop on an *existing* action would be MAJOR), **and set `minimumSupportedRelease` in `src/index.ts`** — read the current standard off a piece from the last merged wave (`grep minimumSupportedRelease packages/pieces/community/gmail/src/index.ts`) rather than guessing, and never leave the piece's stale default. **Sanity-check whatever you copy against the latest actually-shipped release** — that value has itself been wrong more than once (below), so confirm it is ≤ the newest release tag before trusting it (`gh release list -R activepieces/activepieces -L 3`, or the version `main` itself declares). Both directions bite:
   - **Floor too low** → engines predating CF.1's canvas filter (anything ≤ `0.86.3`) load the piece and surface every `audience:'ai'` atomic in the *human* step picker. This caused the workstream's only revert: #13952 (firecrawl+apify) shipped at `0.30.0` → reverted #14377 → re-landed #14378 → floor corrected again in #14440; github repeated it (#14463), google-docs needed it added during its re-land (#14519).
   - **Floor above the latest *shipped* release** → `isSupportedRelease` filters that version out of every read path and the catalog keeps serving the piece's *previous* version: published, never served ([PIE-372](https://linear.app/activepieces/issue/PIE-372)). Acceptable when the release is imminent — the atomics stay dark until it ships — but say so in the PR, and never "fix" it by lowering the floor.
8. **`outputSchema`** — every atomic ships with one, but it is authored **after Tier-2** (the schema requires the real captured run output). See the outputSchema section below; don't guess a shape here.

## Tier-1 (hard gate, every atomic)
```
npx turbo run build --filter=@activepieces/piece-<name>     # tsc -p tsconfig.lib.json
npx eslint --fix <new files> && npx eslint <new + edited files>
```
0 errors required. `@typescript-eslint/no-explicit-any` is a **warning** in pieces (existing actions use `catch (error: any)`) — match the piece; warnings don't block.

## Tier-2 (required automated connection test, every atomic where a connection is obtainable)
**Prerequisites (stand these up before Tier-2, not during):** the AP dev stack running locally (`npm start` → API `:3000` + UI `:4200`), the piece hot-loaded via `AP_DEV_PIECES=<piece>` in `.env.dev`, and a **real connection for the vendor seeded through the UI** on that instance — connect the account once and the platform handles token refresh. A vendor you cannot get an account for is the one exemption: those atomics ship Tier-1-only and flagged, never silently skipped.

Run each new atomic against the **seeded real connection** on the local dev instance and assert success + output shape. Harness = the JWT `test-step` REST path (NOT the MCP/OAuth path): build a throwaway flow → EMPTY trigger → add the PIECE step with `input.auth = "{{connections['<externalId>']}}"` → `POST /v1/sample-data/test-step` → poll `flow-runs/:id` → assert `SUCCEEDED` + shape → delete the flow. The four steps above are the whole harness — a ~150-line script drives them; the AI-ready planning workspace (Ibrahim's — ask him) has a working Python reference (`verify_atomic.py`) if you'd rather not rewrite it. **Save each atomic's SUCCEEDED run output JSON to disk** — it is the required source payload for the outputSchema step below.

**`SUCCEEDED` is a weak gate — read the captured payload.** A call that 200s while returning the wrong body still reports `SUCCEEDED`: senja's `get_testimonial`/`fetch_testimonial` passed Tier-2 returning the response *envelope* instead of `response.body.testimonial`, and the pieces team fixed it post-merge (`f1391eb`). Diff every captured JSON against the vendor's documented response shape, and exercise the atomic on a record with **real content** — a minimal/empty response yields a thin outputSchema the team then has to extend (stripe `ddf3eb0` added the missing charge `payment_method_details` / `outcome` subtrees).

**Pilot-proven gotchas:**
- **Restart the dev server after authoring.** The engine caches/bundles each dev piece at boot (`cache/v12/...`); rebuilding the source dist does NOT refresh the running engine — a new action returns `ENTITY_NOT_FOUND` from `getPieceAndActionOrThrow` until restart. Stop the stack (`pkill -f 'turbo run serve'` + the tsx/vite/esbuild watchers), relaunch `npm start`, wait for `:3000`+`:4200`.
- **New scopes need a connection re-consent.** If step 3 added an OAuth scope, the existing seeded connection's token lacks it → write atomics fail until the user reconnects the account in the UI (re-granting consent). Read-only atomics (covered by existing scopes) test immediately. Destructive atomics: act on a throwaway resource + clean up; vendors with no obtainable account ship Tier-1 + flagged-pending. **Symptom (gmail wave-2):** scope-blocked calls don't always return a clean 403 — the `@googleapis` client surfaces them as `invalid_request` (the action's `error.code===403` handler won't fire). A *uniform* `invalid_request` across exactly the new-scope atomics while same-connection read/send atomics pass = the re-consent wall, not a bug.
- **Don't ship a scope you can't verify. Split the PR by scope tier.** When a piece's surface splits into in-scope (testable now) vs. scope-gated (needs a new OAuth scope + re-consent you can't do, e.g. AFK), ship a **scope-neutral PR** of the fully-Tier-2'd in-scope atomics now (no `auth.ts` change), and hold the scope-gated atomics + the `auth.ts` scope add for a **follow-up PR** that the user greenlights + a re-consented connection verifies. A consent-scope expansion on a flagship piece is an all-users decision — propose it only when it's been OK'd or can be verified. (gmail wave-2: Tier A 19 shipped, merged as #14565; Tier B 11 + `gmail.modify`/`gmail.labels` deferred. gcal: 13 in-scope shipped, merged as #14520; 15 calendar/calendarList/ACL deferred.)
- **Test against the user's REAL account safely.** The seeded connection is the user's actual account: send only self→self, never live-run permanent-delete (`batchDelete`) — Tier-1 only, flag it; clean up every created draft/label/event; trash/untrash only your own test artifacts. Note any leftover test items the user must clear (you can't trash them without the modify scope).

## outputSchema (required — every Tier-2-passed atomic ships with one)
Author per the AP repo's **`piece-output-schema` skill** (`.agents/skills/piece-output-schema/` — on `main` since #14404, so read it from the branch you're on; an older clone may predate it). That skill owns the how (curated-tree mental model, formats, `labelKey`/`itemLabel`, wiring). Phase-3 specifics on top:
- **Source payload = the Tier-2 captured output** for that atomic — never docs or a guessed shape. **No Tier-2 pass (no obtainable connection) → NO schema**: ship the atomic Tier-1-only + flagged, and leave its schema to a Phase-4 pass — same principle as "don't ship a scope you can't verify".
- **Skip deliberately per the skill's step-kind table** — empty-body deletes (`{}`/`''`/204) and `custom_api_call` get no schema; record the skips in the PR body so they don't read as omissions.
- Schemas live in the piece's `src/lib/output-schemas.ts`; wire `outputSchema: <name>` on each new atomic; factor shared field-sets (a twin reusing the original's `run()` shares its schema const). #1 correctness bug: `children`/`listItems` paths are **relative to the parent**. Never surface `config`/`headers`/tokens.
- **Cover the whole piece, not just your atomics.** On every one of the 12 merged waves a maintainer pushed a follow-up commit schematizing the piece's *pre-existing* actions and triggers (serp-api `604fa13`, trello `549bea8`, drive `2b9606f`, discord `79b901b`…). If the piece has no `output-schemas.ts` yet you are the one creating it — schema the existing actions whose output you can capture on the same seeded connection, in the same PR.
- Wiring is metadata-only (doesn't touch `run()`): **re-run Tier-1 after**, no Tier-2 re-run needed; rebuild + restart the dev stack and confirm the friendly tree renders on one atomic. The step-7 PATCH bump covers it — one bump per piece, not a second one.

## Fan-out (multi-piece batches)
**Authoring one piece? Skip to the PR rules below** (Greptile cap, rebase, worktree isolation) — they apply to any PR. The subagent-cluster mechanism in this paragraph is only for running several pieces at once.

Waves 1–8 ran as a **manual subagent cluster-fan-out**, NOT the automated `batch-workflow.js` Workflow pipeline. Mechanism: the main thread spawns one authoring subagent per piece (a cluster of parallel `Task`/agent calls), each equipped with (a) **read** these refs (piece-builder + this skill's `atomic-templates.md` + `ai-metadata.md` + the AP repo's `piece-output-schema` skill), and (b) the per-piece spec + paths + Tier-1/2 commands as structured args (a fresh subagent inherits neither). Verification is **main-thread-verified**: the main thread re-runs the Tier-1 gate (tsc/eslint/build) and drives Tier-2 itself rather than trusting a subagent's completion claim. No worktree isolation for authoring (disjoint piece files per branch). Group into reviewable PRs by batch/vendor; off fresh `upstream/main`; `SKIP_CHECK=1 git push origin HEAD`; no-AI voice on public text.

**Keep each PR under Greptile's 100-file limit.** #13946 shipped at 116 files and Greptile skipped it **silently** — that wave got no automated review at all, and nothing in the PR says so. Split a wave by piece before it crosses the cap. Greptile is also unreliable on *re*-review (it acknowledged then never delivered on wave-7 github and on wave-8, across repeated `@greptileai` triggers and pushes): when it no-shows, re-verify your fixes yourself with a live Tier-2 run and record that in the PR thread rather than waiting on it.

**Keep the branch a clean rebase on `upstream/main`.** Merging `main` *into* a fork branch drags already-merged, unrelated files into the PR diff — on #13926/#13929/#13930 that pulled in `benchmark/k8s-sandbox.yaml`, tripped GitGuardian's forked-repo secret scan, and cost all three PRs a maintainer-authored squashed replacement (#14519 / #14520 / #14565). Rebase to take upstream changes; if a PR has already accumulated merge commits, squash it onto fresh `upstream/main` yourself before asking for review.

**PR isolation when the dev branch is dirty (wave-2 pattern):** when the dev branch carries unrelated WIP (dev-page, other pieces, `.env.dev`), isolate each PR in a throwaway worktree off fresh `upstream/main` (`git worktree add -b <branch> <path> upstream/main`), replicate only that piece's files, commit + push with `--no-verify` (husky `_/husky.sh` is missing in a worktree), open the PR against `upstream:main`. **Gotcha:** a worktree's symlinked `node_modules` breaks tsc's `@activepieces/*` resolution (even *untouched* pieces fail tsc there) — so **run the tsc/eslint gate in the MAIN clone** (or rely on the Tier-2 runtime pass, which proves compilation); the worktree is for clean git isolation only. Confirm no upstream drift on the piece since your branch base (`git diff BASE..upstream/main -- <piece>`) before a wholesale file copy.

## After merge — merging is not shipping
A merged atomic reaches agents only after four more things happen, and this workstream lost weeks to every one of them (waves 1–8 sat invisible in **every** environment from late June until the `0.87.0` release on 2026-08-06). **A wave is done when `ap_search_actions` returns its atomics on cloud — not when the PR goes green.**

1. **Publish** — `release-pieces.yml` publishes the piece on merge (npm + the cloud catalog). Automatic, and the reason step 7's floor is load-bearing: publishing happens whether or not the piece can be served.
2. **Release** — a version whose `minimumSupportedRelease` exceeds the deployed release is stored but filtered out of every read path, so the catalog keeps serving the piece's *previous* version. Full root-cause writeup: **PIE-372**.
3. **Reconcile** — cloud's `tool_search_index` updates only when a publish fires the reconcile hook (#14447). Until it runs, `piece_metadata` holds your atomics and `ap_search_actions` does not return them. An `audience` flip updates the row **without** re-embedding, so a demotion propagates on the next publish at no embedding cost.
4. **Self-host** — the sync stores an `ai`-stripped row per `name:version` and never re-fetches it (PIE-378). Until that fix ships *and* the pieces republish, no self-hosted install receives the atomics regardless of everything above.

**Verify the served value, never the deploy** — a green deploy proves nothing:
- **`ap_search_actions` scoped with `pieceName`** — confirm the response says `mode:"semantic"`, that each new atomic returns, and that each action you demoted does **not**. This is the only surface the demotion actually gates.
- **`ap_get_piece_props` on one atomic** — confirms `aiMetadata` and the `outputSchema` tree are served, not just merged.
- **Do not use `ap_research_pieces` as the fence test.** It passes `audience: ALL` by design and returns `'human'` actions too, so it will look like the demotion failed when it didn't. Same for the web agent tool picker. Likewise the keyword floor (`mode:"keyword"`) applies **no** audience filter — with no embedder configured, or on a τ-abstained query, an agent can still be handed a `'human'` action.
